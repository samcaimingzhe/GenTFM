# GenTFMv2 代码审查：与 V1 的比较及损失记录

> 本文审查的是原版 **GenTFMv2**。当前目录为 **GenTFMv2.1**，其 `best.pt` 已改为按最低单步训练 loss 选择；模型与归一化问题仍与 V2 相同。新规则见 [README.md](README.md)。

审查日期：2026-09-25  
范围：`GenTFMv1`、`GenTFMv2` 的模型、训练循环、合成数据适配器与相关说明文档。本文包含静态代码审查、模型参数统计，以及使用提供的 `validation_set.pt` 对 V2 最佳 checkpoint 所做的 CPU 验证复算；未进行完整训练或生成质量基准测试。

## 总体判断

GenTFMv2 是一次实质性的架构改写，不只是把 V1 的 Transformer 换个名字。它保留字段轴，使用按列的诱导点注意力、行内字段交互和按字段对齐的上下文交叉注意力。这些设计更贴合混合类型表格，也使默认模型参数量从 V1 的 **18,350,112** 降至 V2 的 **3,404,571**。

训练流程也有改进：V1 按最低**单步训练损失**保存 `best.pt`；V2 改为按固定验证任务的损失选择。V2 还改进了类别交叉熵的聚合方式。不过，现有代码存在可能使损失极端放大的归一化风险，以及续训时 `best_loss` 与 `best.pt` 脱节的风险。注意力结构更细致，不能单凭结构推断 V2 的生成质量、训练速度或稳定性优于 V1。

## 一、架构与目标函数的变化

| 项目 | GenTFMv1 | GenTFMv2 | 评价 |
| --- | --- | --- | --- |
| 上下文表示 | 每行一个 `hidden_dim=384` 的向量；在行之间做 Transformer 注意力 | 每行保留最多 40 个 `field_dim=128` 的字段向量 | V2 保留字段边界和对齐信息；代码没有显式列 ID |
| 上下文编码 | 4 层整行 Transformer | 默认 2 层列方向诱导点注意力，再做 2 层行内字段交互 | V2 更适合区分列内分布与行内依赖 |
| 生成网络 | 目标行整体读取上下文行 | 每个目标字段读取相应的上下文字段，每层再进行行内交互 | V2 有更强的字段对齐约束 |
| 默认参数量 | 18,350,112 | 3,404,571 | V2 约为 V1 的 19%，但参数少不代表计算必然更快 |
| 类别损失聚合 | 先对每个类别字段求均值，再对字段求均值 | 对所有有效的“表 × 字段 × 目标行”求总和后除以数量 | V2 避免少见字段因“每字段等权”而被放大 |
| 最佳模型选择 | 最低单步训练损失 | 最低固定验证损失 | V2 的选择依据更稳健 |

代码位置：[V1 上下文编码器](../GenTFMv1/gen_tfm/model.py#L107)、[V1 生成网络](../GenTFMv1/gen_tfm/model.py#L174)、[V2 上下文编码器](gen_tfm/model.py#L264)、[V2 生成网络](gen_tfm/model.py#L318)、[V1 类别损失](../GenTFMv1/gen_tfm/model.py#L364)、[V2 类别损失](gen_tfm/model.py#L561)。

V2 所谓的“CLS 介导的行内交互”需要更精确地理解：实现把 CLS token 与字段 token 放在同一序列里做完整自注意力，因此字段之间也能直接注意彼此；CLS 另外产生一次全局更新。它并非只允许字段通过 CLS 交换信息。[实现](gen_tfm/model.py#L247)

计算成本需要单独测量。V2 的生成块把张量整理成 `B × F` 条字段序列，分别对 `M` 个目标行和 `K` 个上下文行做交叉注意力；默认最多 `F=40`。相比 V1 的整行交叉注意力，注意力配对数多了字段维度，同时 V2 的字段宽度较小。代码仍会对填充字段执行部分计算，最后才将其清零。因此不能从参数量推断吞吐量。[实现](gen_tfm/model.py#L330)

## 二、`loss`、`validation_loss`、`best_loss` 的准确含义

模型单次计算的总损失为：

```text
总损失 = CFM 流匹配损失
       + cat_loss_weight × 类别交叉熵
       + mask_loss_weight × 观察掩码 BCE
```

默认权重分别为 `0.8` 和 `0.0`；连续值的流匹配权重为 1，类别及掩码维度在流匹配项中的权重为 `discrete_flow_weight=0.05`。[损失实现](gen_tfm/model.py#L540)

| 名称 | 计算时机及数据 | 记录位置 |
| --- | --- | --- |
| `loss` | 当前随机合成训练 batch 上、**本步参数更新前**计算的总损失 | `loss_history.csv` 每步一行、`train_losses.npy`、训练日志 |
| `validation_loss` | **本步参数更新后**，在固定验证表、固定随机划分、固定时间和噪声上的总损失均值 | `validation_history.csv` 和验证日志，仅验证步有值 |
| `best_loss` | 截至当前最低的 `validation_loss`；非验证步沿用此前值 | `loss_history.csv`、checkpoint、训练日志 |

默认每 1000 步验证，也会在每次训练会话的第一步和最终步验证。默认验证集为 8 张表；对于默认 768 行、`min_ctx=5`、`max_ctx=200` 的设置，每张表使用上下文大小 **5、102、200**，共 24 个表与上下文大小组合，最后等权平均。[验证实现](scripts/train.py#L247)、[保存逻辑](scripts/train.py#L341)

固定验证随机性本身实现正确。小模型上连续调用同一验证函数两次，得到完全相同的数值。V2 也在验证时切换到 `eval()` 并在结束后恢复模型原有状态。[随机性隔离](scripts/train.py#L202)、[验证实现](scripts/train.py#L254)

**这些数值不能直接横向比较。**`loss` 与 `validation_loss` 来自不同数据，并且分别对应更新前和更新后的模型。训练 batch 的 CFM 项按 batch 内有效维度加权平均；验证则先逐表计算损失，再对表与上下文大小等权平均。此外，`latest.pt` 中的 `best_loss` 是历次最佳验证值，不一定是 `latest.pt` 当前权重的验证值。正常情况下，`best.pt` 才对应创下该最佳值时的权重。

## 三、需要优先修复的问题

### P1：小上下文的归一化可使 CFM 损失爆炸

V2 使用上下文行的均值和标准差归一化**上下文及目标行**，计算式为 `(x - context_mean) / (context_std + 1e-6)`。[归一化实现](gen_tfm/model.py#L69)、[训练中的调用](gen_tfm/model.py#L524)

若一个连续字段在 5 行上下文里全为 0，而某目标行为 1，那么归一化后的目标是 **1,000,000**，其平方约为 **1e12**。该数值已用 `normalize_mixed_batch` 的最小样例复现。流匹配目标包含这个归一化目标，因此单个近常数列就可能主导总损失。[训练中的归一化](gen_tfm/model.py#L524)

**提供验证集后的实测结果。**使用 `/Users/caimingzhe/Downloads/validation_set.pt` 和 `/Users/caimingzhe/Downloads/checkpoints3.33/best.pt`，按验证代码的种子和任务顺序在 CPU 上复算了全部 24 个任务。下表编号从 0 开始；4 个极大损失任务全部发生在 `K=5`：

| 验证表 | `K` | 最小归一化分母 `std + 1e-6` | 最大归一化目标绝对值 | 模型总损失 |
| --- | ---: | ---: | ---: | ---: |
| 0 | 5 | `1e-6` | `4.07e6` | `1.046e11` |
| 1 | 5 | `1e-6` | `4.02e6` | `4.957e10` |
| 3 | 5 | `1e-6` | `4.24e6` | `1.639e11` |
| 7 | 5 | `1e-6` | `7.00e6` | `1.186e11` |

`K=5` 的八表平均损失约为 `5.458e10`，而 `K=102`、`K=200` 分别约为 `2.08`、`2.21`。上述四个任务几乎贡献了全部复算损失。以表 0 为例，总损失约 `1.046e11`，类别交叉熵约 `1.53`；大值来自 CFM 项。异常上下文列的五个值完全相同，但整表标准差约为 1，且整表各列有 2–6 个不同取值。部分异常列确实同时被编码为类别列和连续列，**也有未重复编码的异常列**；因此仅删除重复列不能完全解决问题。[合成数据列选择](gen_tfm/prior.py#L213)

24 个任务在本机 CPU 上重算的均值为 `1.8192e10`，而第 16000 步 `best.pt` 记录的 `best_loss` 为 `1.7216e10`，相差约 **5.7%**。提供的验证集设置与 checkpoint 训练设置一致，但 checkpoint 没有保存验证集哈希；原训练设备与本机 CPU 的浮点计算也可能不同。因此不能断言这两个数字应逐位相同。两者的量级及异常任务集中位置一致；近常数列造成极大损失已在所提供的验证集上得到确认。

建议先在正式训练中记录 `cfm_loss`、`cat_loss`、`mask_loss`，以及每个验证任务的表编号、上下文大小、最小标准差和最大归一化目标值。然后为近常数列设计训练与生成阶段一致的尺度处理；只修改训练归一化会使推理分布不一致。[推理时的上下文尺度](gen_tfm/generation.py#L62)

此外，训练循环只对 `validation_loss` 做有限值检查；它在 `loss.backward()` 和 `optimizer.step()` 之前没有检查训练 `loss` 是否有限。数值不稳定时，应在更新权重前检查损失和梯度。[训练循环](scripts/train.py#L329)

### P1：续训时 `best_loss` 和 `best.pt` 可能失去对应关系

恢复训练从指定 checkpoint 读取 `best_loss`，却只在目标 `best.pt` **不存在**时复制旧文件；如果它已经存在，就不核对文件中的步数、损失及来源。[恢复逻辑](scripts/train.py#L288)

一个具体场景：

1. `latest.pt` 在第 10000 步记录最佳验证损失 8。
2. 第 12000 步验证得到 6，更新了 `best.pt`。
3. 下次保存 `latest.pt` 之前训练中断。
4. 从第 10000 步的 `latest.pt` 续训，程序读取标量 8，但保留记录 6 的 `best.pt`。
5. 恢复后的第一次验证若得到 7，程序会认为它优于 8，并把原先更好的 `best.pt` 覆盖。

默认每 1000 步验证、每 10000 步保存 `latest.pt`，所以这一情况存在实际窗口。[验证与周期保存](scripts/train.py#L343)

应在恢复时读取并核对目标 `best.pt` 与来源 `best.pt` 的损失、步数及验证设定，明确决定保留哪一份；还应避免让不同运行遗留的 `best.pt` 被误认为当前运行的最佳文件。

### P1：续训可以悄悄改变损失定义，却沿用旧的最佳阈值

模型权重的严格加载只核对张量名称与形状。`cat_loss_weight`、`mask_loss_weight` 和 `discrete_flow_weight` 是影响损失数值的配置，却不会使权重形状发生变化。恢复代码没有比较 checkpoint 的 `model_config` 或完整 `train_config` 与当前参数；验证集设置检查也不包括这些损失权重。[模型配置](gen_tfm/model.py#L441)、[验证设置检查](scripts/train.py#L216)、[恢复逻辑](scripts/train.py#L290)

如果续训时改变这些参数，新旧 `validation_loss` 不再是同一指标，沿用旧 `best_loss` 选模型就没有意义。建议对影响损失与验证定义的参数做强制一致性检查；允许变更时，重新建立最佳值基准，并在日志中标明新会话的指标定义。

## 四、日志与文档的问题

1. **同一行含有不同语义的值。**`loss_history.csv` 的 `loss` 是当前步更新前的训练值；`best_loss` 是更新后验证的历次最小值，并且大多数步不会重新计算。建议改名为 `train_loss`、`best_validation_loss`，并在发生验证时记录 `validation_loss`。当前验证值虽另存在 `validation_history.csv`，但不方便与训练曲线对齐。[CSV 字段与写入](scripts/train.py#L53)
2. **续训后的验证历史可能出现重复或倒序步数。**`loss_history.csv` 是追加式日志，绘图恢复前缀时按步数选取较新的记录；`validation_history.csv` 则直接追加，没有 session ID、恢复边界或去重处理。续训如果从较旧 checkpoint 开始，验证历史会同时保留旧分支与新分支。[训练历史恢复](scripts/train.py#L56)、[验证历史写入](scripts/train.py#L351)
3. **指南与 V2 实现矛盾。**中文训练指南仍写 `best.pt` 由最低单步训练 loss 选出，而 V2 实际使用固定验证损失。该指南若用于 V2，需要改写。[现有指南](../TRAINING_GUIDE_ZH.md#L479)、[V2 实现](scripts/train.py#L343)
4. **只有总损失，不利于诊断。**尤其面对 `1e10` 量级的值，仅看 `loss` 和 `best_loss` 无法判断问题来自连续值的流匹配、类别交叉熵，还是少数验证任务。建议分别记录三个分量，并记录每个上下文大小的验证均值与极值。[总损失返回](gen_tfm/model.py#L583)

固定验证只有 8 张表，每张表只评估 3 个上下文大小。它可以稳定地比较同一批任务，却未必代表所有合成表和训练时均匀采样的上下文大小；若其中一个任务的归一化值极大，均值还会被其主导。这是验证指标的覆盖范围问题，不是随机性没有固定。

## 五、可精简及需要明确用途的部分

- **默认未使用的掩码目标。**`mask_loss_weight=0`，但每步仍计算 mask head 与 BCE。生成时也会先抽样观察掩码，再因“无缺失值”协议把它强制改为全 1。可以按配置跳过无效计算，同时保留将来支持缺失值的代码路径。[训练](gen_tfm/model.py#L578)、[生成](gen_tfm/model.py#L642)
- **两次连续字段标准化。**合成数据适配器先用整张表的统计量标准化，V2 随后再用上下文统计量标准化。普通情况下两次仿射变换大体抵消；在极小方差时，平滑常数使其不再严格抵消。这两层预处理应统一梳理，并与推理阶段保持一致。[合成数据标准化](gen_tfm/prior.py#L227)、[模型标准化](gen_tfm/model.py#L526)
- **填充字段的注意力计算。**模型按最大字段数构造列注意力与按字段交叉注意力，即使实际表的字段更少，仍执行部分无效字段计算，再按 `field_mask` 清零。这是性能优化机会，是否值得改动需要用真实 batch 做性能剖析。[列注意力](gen_tfm/model.py#L295)、[生成交叉注意力](gen_tfm/model.py#L330)
- **两个 tokenizer 并非简单重复。**上下文编码器与目标流网络都要把各自输入转换成字段 token，目前使用结构相同但参数独立的 tokenizer。共享参数是可研究的选择，不能直接把其中一个删掉。[编码器](gen_tfm/model.py#L280)、[生成网络](gen_tfm/model.py#L353)

续训还有一个再现性限制：checkpoint 保存模型、优化器和调度器状态，但没有保存 Python、NumPy、PyTorch 的训练随机状态，也没有保存合成先验采样器的内部进度。因此恢复后不会精确延续原来的合成任务序列；这不影响固定验证集的重复计算，却影响训练轨迹的严格复现。[checkpoint 内容](gen_tfm/checkpoint.py#L29)、[训练入口设种子](scripts/train.py#L480)

## 建议的处理顺序

1. **先定位极大损失的来源。**增加训练与验证的损失分量、分上下文大小统计、最小标准差及最大归一化目标值；检查训练 loss 和梯度是否有限。
2. **解决近常数列的尺度问题。**训练与推理共同采用经过验证的处理方式，并重新观察损失分布及生成质量。
3. **修复续训一致性。**核对 `best.pt`、恢复 checkpoint、验证集和损失定义；明确处理旧分支日志与最佳权重。
4. **整理指标命名和文档。**让 `train_loss`、`validation_loss`、`best_validation_loss` 的名称、时间点和图表一致。
5. **最后做公平基准。**在相同数据、算力预算和评估集上比较 V1/V2 的生成质量、单步耗时与显存。当前只能判断设计差异，不能据此宣称 V2 已取得更好性能。
